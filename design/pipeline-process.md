# 🔧 Process Pipeline — กระบวนการพัฒนา Monster Speller (Human-in-the-Loop เท่าที่จำเป็น)

> **บทบาท:** Process Engineer — วาง pipeline, ออกแบบเครื่องมือ, จัดการกระบวนการ
> ให้งานไหลจาก "ไอเดีย" → "เกมที่ deploy ได้" โดย **automation รับทุกอย่างที่เครื่องทำได้
> 100%** และ **คนแตะเฉพาะจุดที่ต้องใช้ดุลยพินิจ** (ความสวย/ความสมดุล/อนุมัติ)
>
> **เอกสารคู่:** บท 8 (แผน dev) · บท 9 (Agile Kanban) · บท 14 (สถาปัตยกรรม) ·
> `prompt-processability-spec.md` (สัญญา PEP) · `walk-cycle-spec.md` (สเปกท่าเดิน)

## 1. ภาพรวม Pipeline (6 ระยะ + วงวนเรียนรู้)

```
┌──────────┐   ┌──────────┐   ┌──────────────┐   ┌───────────┐   ┌────────────┐   ┌────────┐
│ 1.PLAN   │ → │ 2.SPEC   │ → │ 3.PRODUCE    │ → │ 4.VERIFY  │ → │ 5.INTEGRATE│ → │ 6.SHIP │
│ ผู้เรียน  │   │ เอกสาร   │   │ AI สร้างงาน   │   │ ตรวจอัตโนมัติ│   │ ประกอบเข้าเกม│   │ Pages  │
│ เป้าหมาย │   │ สัญญา PEP│   │ + คนอนุมัติ   │   │ + คนตรวจตา │   │ + เทส E2E  │   │ deploy │
└──────────┘   └──────────┘   └──────────────┘   └───────────┘   └────────────┘   └────────┘
     │              │               │                 │               │               │
     └──────────────┴───────────────┴─────────────────┴───────────────┴───────────────┘
                                       ▲  feedback (เทสจริงกับนักเรียน → ย้อนกลับข้อ 1/3)
```

**หลักคิด:** แต่ละระยะจบด้วย **Gate** (ประตูผ่าน) — ไม่ผ่านไม่ข้ามระยะ
เครื่องทำได้ → เครื่องทำ · เครื่องทำไม่ได้ → คนทำ (ดูตาราง ข้อ 3)

---

## 2. รายละเอียด 6 ระยะ (งาน · เครื่องมือ · Gate)

### ระยะ 1 — PLAN (ออกแบบการเรียนรู้)
| รายการ | รายละเอียด |
|---|---|
| งาน | ตั้งเป้าหมายการเรียนรู้ · วิเคราะห์ผู้เรียน (บท 3) · กำหนดขอบเขตเกม (บท 4-5) |
| ผลลัพธ์ | User Stories + Acceptance Criteria (บท 8.2/8.4) |
| Gate | ผู้เชี่ยวชาญการสอน (ครู/นักวิชาการ) **อนุมัติ** เนื้อหา+ระดับความยาก |
| HITL | ✅ **คน** — เนื้อหาการเรียนต้องคนตัดสิน (ไม่มีเครื่องมือวัด "สอนดี") |

### ระยะ 2 — SPEC (เขียนสัญญาให้เครื่องมือทำงานได้)
| รายการ | รายละเอียด |
|---|---|
| งาน | เขียนสเปกงานกราฟิกตาม **PEP** (พื้น `#00ff00` + กริด + ห้ามเงา) · สเปกท่าเดิน (walk-cycle-spec) · กำหนดชื่อไฟล์/ที่วาง (📦 ในทุกพรอมต์) |
| ผลลัพธ์ | พรอมต์ PEP พร้อมใช้ · sprite-spec.json · manifest schema |
| Gate | `tests/check-links.py` (ลิงก์เอกสารไม่เสีย) + คนตรวจสเปกครบ |
| HITL | ⚠️ **ครึ่งคน** — คนเขียนพรอมต์/ตรวจสเปก แต่เครื่องตรวจลิงก์/โครงสร้างอัตโนมัติ |

### ระยะ 3 — PRODUCE (AI สร้าง → คนคัด)
| รายการ | รายละเอียด |
|---|---|
| งาน | คัดลอกพรอมต์ PEP → AI ภาพ → วาง PNG ที่ `public/assets/ai/` |
| ผลลัพธ์ | ไฟล์ `<name>-sheet.png` (AI ดิบ — ห้ามเข้าเกมตรง ๆ) |
| Gate | — (ยังไม่ตรวจ — ตรวจในระยะ 4) |
| HITL | ⚠️ **ครึ่งคน** — AI สร้าง · คนเลือก/คัดเวอร์ชันที่ใช่ (เครื่องตรวจไม่ได้ว่า "สวย/ตรงอารมณ์") |

### ระยะ 4 — VERIFY (ตรวจอัตโนมัติ + คนตรวจตา) ⭐ วงจร PEP
| ขั้น | เครื่องมือ | ผ่านเมื่อ | คน? |
|---|---|---|---|
| 1 | `ai-sprite-process.py --require-check --drop-flat --dedupe` | exit 0 (กริดตรง · ไม่มีเฟรมหลอก/ซ้ำ/เงา/ติดขอบ) | ❌ เครื่อง |
| 2 | เปิดเฟรม `_00`–`_NN` ดูด้วยตา | ท่าต่างกันจริง · ตรง Character Bible · สวย | ✅ **คน** (30 วินาที/ชุด) |
| 3 | ตัดสินใจ: ผ่าน → ระยะ 5 · ไม่ผ่าน → แก้พรอมต์/gen ใหม่ (วนข้อ 3-4) | — | ✅ **คน** |
| HITL | **คนแตะแค่ขั้น 2-3** — เครื่องกรองของเสียให้ก่อน เหลือให้คนตัดแค่ "สวย/ไม่สวย" | | |

### ระยะ 5 — INTEGRATE (ประกอบเข้าเกม)
| รายการ | รายละเอียด |
|---|---|
| งาน | manifest → SpriteRenderer (บท 7.6) · ใส่ wordBank/ด่าน · ต่อระบบคะแนน/คำใบ้ |
| ผลลัพธ์ | โค้ดผ่าน typecheck + unit test + lint · E2E ผ่าน (Playwright) |
| Gate | `npm run typecheck` + `npm run test` + `npm run test:e2e` → ผ่านหมด |
| HITL | ❌ เครื่อง (โค้ด/เทสเป็นสิ่งที่เครื่องตรวจได้ 100%) |

### ระยะ 6 — SHIP (ปล่อยจริง)
| รายการ | รายละเอียด |
|---|---|
| งาน | build (`dist/`) → commit → push → GitHub Pages |
| ผลลัพธ์ | URL เล่นได้จริง |
| Gate | เปิด URL + **คนเล่นผ่านด่านแรกจริง** (smoke test ด้วยคน 1 รอบ) |
| HITL | ✅ **คน** — อนุมัติ release + เล่นตรวจรอบสุดท้าย (เครื่องทำไม่ได้: "สนุกไหม/เล่นได้ไหม") |

### วงวนเรียนรู้ (หลัง SHIP)
เทสกับนักเรียนจริง (บท 11) → เก็บข้อมูล (คะแนน/อัตราผิด/เวลาต่อรอบ) → ย้อนกลับ
ระยะ 1 (ปรับความยาก/คำศัพท์) หรือระยะ 3 (ปรับภาพ) — **บทเรียนทุกครั้งบันทึก
ใน changelog + Kanban card**

## 3. ตาราง Automation vs Human-in-the-Loop

| งาน | เครื่องมือ | อัตโนมัติ | คน? | เหตุผล |
|---|---|---|---|---|
| ตรวจลิงก์เอกสาร | `check-links.py` | ✅ 100% | — | กติกาตายตัว |
| ลบพื้น/ตัดเฟรม/กริด | `ai-sprite-process.py` | ✅ 100% | — | ตามสัญญา PEP |
| จับเฟรมซ้ำ/เงา/ติดขอบ | `--dedupe --drop-flat --check` | ✅ 100% | — | เกณฑ์วัดได้ |
| typecheck / unit / lint | Vitest + tsc + eslint | ✅ 100% | — | โค้ดตรวจได้ |
| E2E flow หลัก | Playwright | ✅ 100% | — | flow ตายตัว |
| เลือกเวอร์ชันภาพ AI | ดูด้วยตา | ❌ | ✅ | "สวย/ตรงอารมณ์" วัดไม่ได้ |
| ตรวจท่าต่างกันจริง | ดูเฟรม | ⚠️ ครึ่ง | ✅ (ตรวจตา) | เครื่องจับซ้ำได้ แต่ "ท่าถูกต้องตามชีวกลศาสตร์" ต้องคน |
| สมดุลความยาก/เนื้อหา | วิเคราะห์ข้อมูล | ⚠️ ครึ่ง | ✅ | เครื่องเก็บ stats · คนตัดสินใจ |
| อนุมัติ release | — | ❌ | ✅ | ความรับผิดชอบต่อผู้เรียน |

**กฎ HITL:** คนแตะเฉพาะจุดที่ (ก) ต้องใช้ดุลยพินิจ (ข) มีความเสี่ยงต่อผู้เรียน
(ค) ต้องรับผิดชอบตามกฎหมาย/จริยธรรม — นอกนั้น automation หมด
**ภาระคนต่อ 1 สินทรัพย์ ≈ 1-2 นาที** (เครื่องกรองของเสียให้ก่อน 90%+)

## 5. ตัวอย่างไหลงานจริง (เดิน 1 การ์ด: "สไปรต์วอล์กเกอร์")

```
[Kanban] Backlog → Ready (การ์ด: สไปรต์วอล์กเกอร์ 4×1)
   │ 1. PLAN      — เนื้อหามาตราตัวสะกดผ่านครูแล้ว (Gate ✅)
   ▼ 2. SPEC      — พรอมต์ PEP 4×1 + walk-cycle-spec (check-links ✅)
   ▼ 3. PRODUCE   — AI สร้าง walker-sheet.png → วาง public/assets/ai/ (คนเลือกเวอร์ชัน)
   ▼ 4. VERIFY    — ai-sprite-process.py --require-check --drop-flat --dedupe
   │                 exit 0 (เครื่อง ✅) → คนดูเฟรม 4 ท่า (✅ ต่างกัน/สวย)
   ▼ 5. INTEGRATE — manifest → SpriteRenderer · typecheck+unit+e2e ✅
   ▼ 6. SHIP      — build → Pages → คนเล่นด่าน 1 (✅) → ปล่อย
   ▼ วงวน         — สังเกต: ผู้เรียนยิงมอนสเตอร์ตัวนี้ผิดบ่อย? → ปรับความยาก/คำใบ้
```

## 6. RACI (ใครทำอะไร — ทีมเล็ก 2-4 คน)

| งาน | PO (ครู/เจ้าของเกม) | Dev | Art (AI+คน) | QA |
|---|---|---|---|---|
| กำหนดเป้าหมายการเรียนรู้ | **A** | C | C | I |
| เขียนพรอมต์ PEP / สเปก | C | C | **A** | I |
| สร้างภาพด้วย AI | I | I | **A** | I |
| ตรวจภาพ (เครื่อง+ตา) | I | C | **A** | C |
| เขียนโค้ด/เทส | C | **A** | I | C |
| อนุมัติ release | **A** | C | C | C |

> A = Accountable (รับผิดชอบสุดท้าย) · R = Responsible (ลงมือ) · C = Consulted · I = Informed
> ทีมเล็ก → รวม R/C ได้ แต่ **A ต้องมีคนเดียว** เสมอ (กันงานหลุด)

## 7. กฎทองของ pipeline นี้

1. **เครื่องกรองก่อน คนตัดสินใจทีหลัง** — ทุกของเสียที่เครื่องจับได้ ห้ามเด้งไปให้คนดู
2. **สินทรัพย์ AI ดิบห้ามเข้าเกม** — ต้องผ่านระยะ 4 (ตรวจ+ตัด) ทุกครั้ง
3. **คนแตะ ≤ 3 จุดต่อสินทรัพย์** — เลือกเวอร์ชัน · ตรวจตา · อนุมัติ — ถ้าเกิน แสดงว่า
   สัญญา PEP หรือเครื่องมือยังไม่ดีพอ → ไปปรับเครื่องมือ ไม่ใช่จ้างคนเพิ่ม
4. **Gate ผ่านแล้วผ่านเลย** — อย่าย้อนกลับขั้นที่ผ่านมาแล้วโดยไม่มีการ์ดใหม่ (กันงานซ้ำ)
5. **ทุกบทเรียน → เอกสาร** — บันทึกลง changelog/PEP spec (เหมือนที่ทำมา: 4×4→4×1,
   เงา → drop-flat, เฟรมซ้ำ → dedupe) กัน AI/ทีมพลาดซ้ำ
